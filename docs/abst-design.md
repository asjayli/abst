# ABST 自动化业务声明测试体系设计

**ABST = Auto Business Statement Testing（自动化业务声明测试）**——自动（Auto）地对业务（Business）的意图声明（Statement）进行测试（Testing）。

**目标层级**：ABST 的目的是 **AI Auto Acceptance（AI 自动验收）**——由 AI 执行、体系的终态产出不是一份测试报告，而是一个**验收决定**（放行 / 转人工）。意图声明是使验收变得可机器计算的支点，测试是达成验收的活动，AI 是执行者（§二）。简言之：**Statement 是对象，Testing 是手段，Acceptance 是目的，AI 是执行者**。这一目的的边界同样诚实：AI Auto Acceptance 只覆盖可机器判定的范畴，`signatory=human` 的声明永远保留人工验收签署（§三）。

> **术语说明（库内定义）**：ABST 脱胎于多个 xDD 方法论但不堆叠其中任何一层：ATDD/BDD/SDD 贡献了声明的三个**抽象级别**（验收标准/业务规则/规格条款），FDD（Feature-Driven Development）贡献了声明的**组织单元**（Feature，特性），DDD（Domain-Driven Design）贡献了声明的**语言基础**（统一语言词汇表，见 §4.6）。这些对象在 ABST 中被归一为同一类一等公民——**意图声明**——体系围绕它运转，而非围绕"AT 层、BT 层、ST 层"运转。业界通行定义中 BDD/SDD/FDD 并非 "BTDD/STDD/FTDD" 的简写，本文仅取其测试侧沉淀物的思想，不沿用其方法论分层结构。各方法论的完整吸收映射见 §十一。

> **两个人工动作的严格定义**（全文禁用裸"背书/签署"）：**入库背书**（§五②）——对声明文本（应然本身）的人工批准，一次性、语义升版即失效；**验收签署**（§五⑥）——对 `signatory=human` 声明每次交付判定的人工验收，发生在 Gate 时点。前者合法化应然，后者验收实然。

> **文档结构**：上篇·思想总纲（为什么）→ 中篇·体系设计（是什么：点 §四 元模型 → 线 §五 生命周期 → 面 §六 Gate/§七 度量 → 演进与边界 §八~§十一）→ 下篇·工程手册（怎么做）。**拆分触发条件**（满足任一即将三篇拆为独立文档）：手册内容超过设计本体；出现第二个实践的手册消费者；全文超 400 行；三篇需要不同的 status 分轨。
## 上篇 · 思想总纲

## 一、第一性原理：业务侧测试到底测什么

技术层测试（UT/IT/E2E）按**代码结构**组织，回答"实现做对了吗"（verification）。它们全绿，仍回答不了"做的是不是要的东西"（validation）：需求是否符合、规则边界是否守住、完成由谁判定、变更影响哪些验证。

**ABST 的定位是对已建成、完善的 UT/IT/E2E 体系的补全，不是替代或平替。** 它站在成熟技术测试体系的肩膀上，只接管技术层照不到的 validation 维度；反过来，技术层本身缺失或不可信时，应先补齐技术层——ABST 不能、也不应用于掩盖"实现对不对"的空白。两者是同一测试体系的两个正交半球：技术层已臻完善的组织，缺的正是 ABST 这一半。

业务侧测试的本质可以归约为一件事：**对"意图"的证伪**。

- 规格条款："单任务并发上限 = 8"——一条意图；
- 业务规则："累计消费满 1000 升银牌"——一条意图；
- 验收标准："会员升级需求做到等级自动迁移即完成"——还是一条意图。

三者的差异不在"种类"，而在两个**属性维度**：**抽象级别**（约束实现细节的程度）与**验收级别**（判定是否需要人背书）。既然被测对象是同质的，测试体系就应该是**一个**，而不是三个。这是 ABST 的全部立论起点：

> **一个被测对象（意图声明），一条生命周期，一个判定机，一个放行函数。** 级别是声明的属性，不是体系的结构。

**动力学一句话：清晰定义应然，循环逼近实然。** 声明先把"应该怎样"明文钉死并经入库背书（应然先行，§五①②），生命周期驱动"实际怎样"向其收敛（实然逼近）：VIOLATED → 修实现 → 复证，STALE → 重新取证，`C(G)` 度量收敛程度，Gate 是收敛完成的闸门。**未经背书的声明不是应然，只是草案**——背书是应然的出生证明，在它之前产生的一切证据与覆盖率都不具验收语义。逼近不是单向的——实然也会反过来暴露应然的错误（声明错，§九），但修正应然的合法通道只有**声明升版 + 人工重新背书**，绝不是悄悄改码去迁就测试。

## 二、执行者前提：ABST 由 AI 执行

ABST 有一个必须显式化的地基假设：**体系的执行者是 AI 大模型，不是人**。这不是实现细节，而是经济性前提——没有它，整个体系的账算不平：

- **成本结构**：声明派生、证据生成、逐变更 diff、逐声明评审，若由人执行，成本高到体系不成立（实践中手写探针的成本已清晰可见）；AI 执行使边际成本趋零，§八的 L1→L4 渗透率演进才谈得上。**若执行者不是 AI，ABST 退化为"认真做的 ATDD"——元模型仍然成立，AI Auto Acceptance 不成立。**
- **信任架构是前提的推论**：AI 执行者会错（误读应然、假绿、误红），所以体系的质量机制不是装饰，而是对执行者不可靠性的系统性补偿——生成者 ≠ 评审者（异构模型交叉）、自报 ≠ 事实（引擎回读）、断言 ≠ 强度（变异度量）、AI 判断 ≠ 终裁（人工背书兜底）。**角色分离在 AI 时代不是淡了，而是更硬了。**
- **确定性与概率性分离**：注册表、判定机、Gate、状态机迁移是**确定性工具**（规模与一致性的底线，每次必跑）；派生、取证、评审是**概率性 agent**（语义与精确的增强层，可以错）。工具是 agent 的安全网，而不是相反。
- **人的位置**：从执行者变为**权威**（入库背书、验收签署、裁决）与**审计者**（抽样复核）。AI 判断是无证据场景的必要工序（§五②），但任何 AI 判断都不是终裁。**最集中的体现是入库背书（§五②）：它是人的权威在流水线中的固定席位，永远前置、永远人工。**
- **能力边界即体系边界**：模型能力决定 L 级别的可达上限；模型升级不需要重设计，只调渗透率旋钮。

## 三、已知边界（诚实条款）

- **可规格化性边界**：体验、美感、部分体感类意图不可机器执行——它们不是"覆盖率缺口"，而是以 `signatory=human`/`WAIVED` 显式建模的一等公民。无人化 100% 是对**可判定范畴**的 100%，范畴边界在注册表里显式可见，而非隐含遗漏；
- **声明自身的正确性**：ABST 证明"实现符合声明"，不能证明"声明本身是对的"。声明（尤其 goal 级）的人工评审是无人化时代人工价值的最后锚点，且该锚点在时间轴上**前置**（§五②），不是体系跑完后的补签。实践实证了更强的一面：声明若从代码反推，体系退化为"给现状盖章机"——**声明的独立性（锚定规格源）决定 ABST 是验证体系还是盖章体系**（§4.1 `derived-from`）；
- **证据的误判率**：AI 派生证据可能假绿/误红，故强度度量与异构评审内嵌于生命周期（§五③），而非外挂可选。
- **设计取舍（Gate 与来源信任）**：Gate 不区分 `derived-from` 来源的 PROVEN——code 来源声明的风险不由门禁承担，而由评审优先级（§4.1）与入库背书（§五②、§十二）前置吸收，且 Gate 硬拒绝 DRAFT 声明（§六）。纯 code 来源声明链支撑的只是"内部一致性放行"，不能宣称验收语义；同理，Gate 不设 level 维度条件，goal 级的人工背书承诺在具象化/入库时点兑现（§12.1），而非每次交付重复。

## 中篇 · 体系设计

## 四、统一元模型：声明–证据–判定（SEV）

ABST 由三个一等概念构成，任何业务侧测试活动都是对这三者的操作：

```
Statement（意图声明）──被证实/证伪于── Evidence（证据）──产出── Verdict（判定）
      ▲ 派生自规格/规则/验收标准            ▲ 载体无关：断言/场景/探针      状态机驱动背书与放行
```

### 4.1 Statement：意图声明

体系的原子对象。一条声明是对系统应然行为/状态的、可判定的陈述：

| 字段 | 语义 |
| --- | --- |
| `id` | 稳定标识（注册表主键，覆盖率与门禁的前置依赖） |
| `text` | 应然陈述（"满 1000 升银牌"，不含实现细节）；用词必须来自统一语言词汇表（Glossary，见 §4.6） |
| `level` | 抽象级别：`mission`（宗旨级，源自产品思想——战略/战术/理想/宗旨/生存条件等顶层意图）/ `goal`（目标级，源自验收标准）/ `behavior`（规则级，源自业务规则）/ `contract`（约束级，源自规格条款） |
| `feature` | 所属特性（组织单元，借鉴 FDD，见 §4.5）：声明归属的最小可交付业务价值单元 |
| `signatory` | 验收级别：`auto`（机器可判）/ `human`（须逐次人工验收签署，如体验类） |
| `executable` | 是否可机器执行；`false` 且 `signatory=auto` 时必须登记豁免（`waiver`），豁免是声明的一部分、随入库背书一并审批（§五②）；`signatory=human` 的不可执行声明不登记豁免，由逐次验收签署承担（§五⑥） |
| `weight` | 业务风险权重（覆盖率按权重加权，避免"用例数"游戏） |
| `version` | 声明版本（语义变更即升版，驱动背书失效与证据失鲜判定） |
| `derived-from` | 派生来源与信任级别：`spec`（从规格/需求文档独立派生，应然基准）/ `code`（从实现代码反推，**信任降级**——只能抓"代码 vs 代码声明的不一致"，抓不到"代码和设计意图一起错"；此类声明背书优先级最高，见 §三） |
| `boundary` | 边界：本声明适用/不适用范围的显式声明（"仅零售会员""不含批量操作"）——边界不明文，判定无意义（§12.3） |
| `elasticity` | 弹性：哪些维度可协商/可调（阈值可配置）、哪些不可动摇（升级语义）——弹性是变化的合法通道，刚性部分是回归的保护对象（§12.3） |
| `endorsement` | 入库背书记录：`{被背书 text+version 的 hash, 背书人, 时间}`——"背书随文本走"的载体；无此记录或 hash 不匹配的声明恒为 DRAFT（§4.3） |
| `waiver` | 豁免三元组：`{理由, 到期时间, 签署人}`——`executable=false` 且 `signatory=auto` 时必填，随入库背书审批，到期回 UNPROVEN（§4.3） |
| `created-at` | 登记时间——背书积压滞留时长与豁免年龄的计算基础（§七） |
| `impl-refs` | 关联实现文件清单——实现变更自动传播 STALE（§九）与 Gate 界定 S(Δ)（§六）的输入 |

`level` 即 AT/BT/ST 的消融点：goal ≈ AT 的验收标准、behavior ≈ BT 的业务规则、contract ≈ ST 的规格条款。但它们在 ABST 中**没有各自的流程**——只是 `level` 取值不同，影响证据载体选择和追溯边方向，不影响生命周期。`mission` 级不对应任何 xDD——它承载产品思想（战略、战术、理想、宗旨、生存条件），多为 `signatory=human`、`executable=false`，是 `refines` 链的根。

**关于意图识别**：意图的层次与识别（战略/战术/理想/宗旨/生存）本身是一个大课题，ABST 不企图消解它，只设立一条底线要求：**顶层意图必须以 mission 声明显式登记并经入库背书**——存在、可见、可被质疑。识别与判断的方法交给背书工序（§五②），其中 AI 判断是必要环节而非可选增强。

### 4.2 Evidence：证据

声明的可执行验证物。**载体无关**：契约断言、GWT 场景、属性测试、数据探针、配置静态校验，都是 Evidence 的装载形式，按声明性质选择而非按"层"分配。其中 contract 级声明的优选载体是**消费者驱动契约测试（Consumer-Driven Contracts）**——由消费方定义期望、提供方验证，天然契合"规格即契约"的语义，且在微服务间可独立于部署执行。证据有三个元属性：

- **强度（strength）**：证据本身的可信度，用变异测试/异构评审度量——AI 生成的证据可能过弱（假绿）或过强（误红），强度不达标 = 无证据；
- **新鲜度（freshness）**：证据对应的声明版本与实现版本。声明升版或实现变更后，旧证据自动失鲜；
- **状态（status）**：`draft`（草案）/ 正式。草案证据合法存在——可作入库背书的评审材料帮人理解声明——但**转正的唯一前提是声明完成入库背书**；背书完成前它不进状态机、不具判定与覆盖率效力（§五②）。

### 4.3 Verdict：判定

判定挂在**声明**上，不挂在用例上（用例红绿只是判定的输入）。状态机：

```
DRAFT（草案）──入库背书（§五②）──────────────→ UNPROVEN（未证）
UNPROVEN ──证据执行通过─────────────────────→ PROVEN（已证）
UNPROVEN（signatory=human）──验收签署（§五⑥）─→ PROVEN（与本次交付绑定）
UNPROVEN/PROVEN ──证据失败──────────────────→ VIOLATED（违反）
VIOLATED ──修复后证据复跑通过────────────────→ PROVEN
已背书声明 ──声明语义升版────────────────────→ DRAFT（背书失效，证据一并失鲜）
已背书声明 ──实现变更（impl-refs 命中）──────→ STALE（失效）──重新取证──→ UNPROVEN
UNPROVEN ──委托登记既有测试/套件─────────────→ DELEGATED ──回读通过──→ PROVEN
DELEGATED ──回读失败────────────────────────→ UNPROVEN
signatory=auto 但不可执行 ──豁免审批（§五②）──→ WAIVED ──到期──→ UNPROVEN
```

`DRAFT` 是注册表的入口态：AI 派生的产物一律只是草案，**未经入库背书的声明不是应然，只是候选**。DRAFT 声明不得产生正式证据、不计入 `C(G)` 分母、被 Gate 命中即转人工（§六）。背书以 `endorsement` 字段记录的 text+version hash 为凭——**背书随文本走，不随 `id` 走**：语义升版即回 DRAFT 重新背书，防止借升版绕过人的裁决。唯一豁免：错别字、格式等**非语义变更**可由背书人抽检确认后保留背书、不升版——背书成本即体系成本，这是体系承认的唯一合法效率出口，其余一律重签。

`signatory=human` 声明的 PROVEN 由验收签署而非机器证据产生，且**与交付绑定**：再次被 Δ 命中即回到待验收（视同 UNPROVEN），须在 Gate 时点重新验收签署——这是"每次背书"的机制化。

只有 `PROVEN` 与合规（未到期）的 `WAIVED` 是"已了结"状态；`UNPROVEN`/`VIOLATED`/`STALE` 是开放债务；`DRAFT` 是背书积压（§七）。`DELEGATED` 是过渡态：**未经回读的委托等于"我说它存在"**，回读通过才迁移为 PROVEN、回读失败回落 UNPROVEN——static 证据须校验目标代码片段仍存在，e2e 委托须读取套件最近一次运行结果，unit 委托须校验断言标记存在（§五④）。

实现变更命中 **DRAFT** 声明：状态不变（无证据可失鲜），但判定机应告警——实现先于背书是应然滞后的危险信号，不是可以沉默的正常态。

**WAIVED 与 `signatory=human` 的选用规则**：不可机器判定且需**每次**验收 → `signatory=human`（如 mission 级声明，持续人工验收签署）；不可判定且**一次性**豁免（`waiver` 登记理由、到期时间、签署人，随入库背书审批）→ WAIVED。二者择一，不叠加。

### 4.4 声明图谱：追溯与覆盖的统一来源

声明之间只有一种边：**`refines`（细化）**，**方向由细化者指向被细化者**：contract → behavior → goal → mission。goal 向上追溯 mission 即沿边方向遍历；规格变更的影响面即沿边**反向**遍历（mission/goal 变更 → 找到细化它的全部下层声明）。这张图谱给出三个关键能力：

- **变更影响面 = 子图遍历**：规格条款变更 → 沿 `refines` 反向找到受影响的规则与目标声明 → 它们的 Verdict 全部置 STALE（实现变更）或回 DRAFT（声明升版）。不再需要人脑记忆"这个改动影响哪些测试"；
- **覆盖率 = 图上的统一函数**：`C(G) = Σ(weight × proved) / Σ(weight × required)`，其中 required = **已背书且未豁免**的声明（即排除 DRAFT 与合规 WAIVED）。**没有三个覆盖率指标，只有一个**——按 `level` 切片查看是它的事后视图，不是三个独立体系各自的 KPI；
- **goal 判定 = 合取**：goal 级声明的 Verdict = 自身证据（如有）与其全部 `refines` 子声明判定的**合取**——任一子声明 VIOLATED，goal 不得 PROVEN。判定机机械执行，实践已验证其价值（子声明失败正确拉红 goal）；
- **可辩护性 = 孤儿检测**：无 `refines` 链抵达任何**已背书** mission 声明的 feature/goal 声明是**孤儿（orphan）**——"无法说清自己服务于什么产品宗旨的存在"。孤儿是纯图遍历可判的，是"需求头像"式不良设计的机制化发现通道：ABST 不审判品味，但强制每个存在物出示辩护。

### 4.5 Feature：声明的组织单元（借鉴 FDD）

声明需要归属，否则注册表只是一堆散点。ABST 借鉴 FDD（Feature-Driven Development）的 **Feature（特性）** 作为声明的组织单元——FDD 的 Feature 定义为"客户可感知的最小业务价值单元"，用规范句式 **`<动作> <结果> <对象>`** 表述（如"计算一次销售的总额"）。在 ABST 中：

- **归属维度**：每条声明通过 `feature` 字段归属一个特性；特性是声明的分组与交付单元，**不是第四个 level**——level 是纵向的抽象级别，feature 是横向的组织维度，二者正交；
- **句式规范**：`text` 推荐采用 FDD 句式（动作-结果-对象），保证声明天然面向业务价值、可被非技术人员审读；
- **交付与门禁的自然作用域**：开发与交付通常以 feature 为单位进行，因此 §六的 Gate(Δ) 中 Δ 的典型粒度就是 feature——"某特性可否无人放行"是最常被问的问题；
- **覆盖率的业务视图**：`C(G)` 按 feature 切片即"每个特性的业务保障完成度"，是比代码覆盖率更适合向业务方汇报的指标。

### 4.6 Glossary：统一语言词汇表（借鉴 DDD）

声明要可机器派生、可机器追溯，前提是**用词收敛**。ABST 借鉴 DDD 的统一语言（Ubiquitous Language），把 **Glossary（词汇表）** 设为注册表的伴生资产：

- **强制约束**：声明 `text` 中的领域名词必须来自 Glossary（"银牌会员""累计消费"），禁止同义词发散（"白银会员""银卡"）；派生环节（§五①）对词表外术语自动告警，进入词表评审或改写；
- **机器价值**：变更影响面计算（§4.4）依赖术语匹配——"规格改了'银牌'的定义"能精确命中所有含该词的声明；词不统一，图谱遍历退化为全文模糊搜索；
- **人的价值**：业务、开发、测试、AI 代理说同一种语言——这也是 BDD"通用语言促进协作"的本义，ABST 把它从"倡导"升级为"注册表约束"；
- **分区**：Glossary 按限界上下文（Bounded Context）分区，同名术语在不同上下文允许不同语义（如"账户"在支付域与会员域），声明的术语解析携带上下文前缀。

## 五、统一生命周期：一条流水线

所有声明走同一条流水线，级别只决定证据载体，不产生分支流程：

```
① 派生 Derive    规格源（openspec/需求文档）变更 → 声明草案 diff（新增/升版/废止），以 DRAFT 入库；
                代码反推允许起步，但标 derived-from: code，信任降级、背书优先级最高
② 背书 Endorse   人工逐条审查声明文本并背书（goal/mission 级加 Three Amigos 会审 + 异构 AI 评审；
                executable=false 声明的 waiver 在此一并审批），写入 endorsement 记录——
                DRAFT → UNPROVEN 的唯一通道；背书绑定 text+version 的 hash，语义升版即失效
③ 取证 Generate  由机器可读 schema 静态生成 manifest（端点清单+输入形状+调用形态），
                探针"填空式"生成 + 异构评审 + 变异强度度量
④ 执行 Execute   证据在 CI 执行，结果回读（编码为 verifyExpr 交引擎校验）；
                委托证据按形态回读：static 校验锚点存在 / e2e 读最近套件结果 / unit 校验断言标记
⑤ 判定 Judge     按 §4.3 状态机刷新 Verdict：实现文件 diff（impl-refs）命中即置 STALE；
                声明文本语义变更即升版回 DRAFT
⑥ 签署 Sign      signatory=human 声明的逐次验收签署在 Gate 时点完成（§六）；
                WAIVED 在此只做到期复核（豁免审批已在②完成）
```

- **派生是事件驱动的**：声明不是一次性编写的文档，而是随规格持续派生的活对象——规格库（如 `openspec/`）的每个变更提案都对应一次声明 diff。behavior 级声明的挖掘手段推荐**事件风暴（Event Storming，DDD 工具）**：从领域事件反推业务规则，规则即声明。**派生必须锚定规格源**：代码→声明→验证代码的链条永远自洽，退化为"给现状盖章机"（§三）；`derived-from: code` 是起步的权宜，不是终态；
- **背书是咽喉，不是滞后待办**：②是整条流水线中**优先级最高的前置任务**——它完成之前，③的产出不进入判定与覆盖率。机制的牙齿有三颗：DRAFT 不计 `C(G)`（§七）、Gate 命中即拒（§六）、CI 检查"DRAFT 声明存在正式 Evidence 记录即报错"。如实说明：机制保证的是**提前取证的产出无效**，而非提前取证不发生——AI 可为背书准备 `status=draft` 的草案证据作评审材料（§4.2），但转正的唯一前提是入库背书。实践已出现典型失败模式：AI 把四册背书当成覆盖率跑完后的"未了结事项"，先在未经批准的应然上取证、算出高覆盖率，签署被推到最后——这是"给现状盖章"的复发形态，只是盖得更精致：覆盖率越高，未经背书的应然显得越可信；
- **取证的杠杆在脚手架**：端点定义的机器可读 schema（如 tRPC 的 zod、OpenAPI）可静态生成 manifest（端点清单 + 输入形状 + query/mutation 形态），探针从手写降为填空——实践中输入形状组合矩阵的试错成本证明该杠杆值得先做。质量门在体系内：异构评审（对照 HEHE 双链中测试链 T→T'→OT 的模式）与变异测试是③的内嵌环节，不是外部最佳实践；
- **两种人工动作不要混淆**（定义见文首术语说明）：②的入库背书针对应然本身，一次性、语义升版失效；⑥的验收签署针对逐次交付判定，发生在 Gate 时点。两者都采用 ATDD 的 **Three Amigos** 会审形式（业务/开发/测试三方），而非单人签字——goal 级声明的分歧大多在三方举例对齐中暴露，这与"先改声明再改实现"（§九）形成闭环。**凡无机器证据可判的声明（mission/goal 级、WAIVED 豁免审批），人工决定前必须经异构 AI 评审**：含"魔鬼代言人"角色，专门质疑"这条 goal 与 mission 的关联是否成立""这条声明的应然合理吗""这条豁免的理由成立吗"，输出结构化意见（支持/质疑/无法判断 + 理由）；人工只裁决分歧与质疑项。AI 评审不是可选增强，是工序——但它不是终裁（§二）；
- **回读是判定的客观化**：执行结果不直接等于 Verdict，须经引擎回读确认"执行真实发生且结果符合预期"（对照 `effectVerifyConf` 的效果回读机制），防止"自报绿但实际红"。委托证据同样适用：`DELEGATED` 无回读不成立（§4.3）。

## 六、判定机与放行函数

无人化的全部判断收敛为**一个函数**——它就是 AI Auto Acceptance 的判定器：

```
Gate(Δ)：变更 Δ（典型粒度为一个 feature 的交付）
  → S(Δ) = 受影响声明子图（由声明图谱遍历得出：Δ 直接触及的声明（impl-refs 命中）
           及其沿 refines 双向闭包）
  → 放行 ⟺  ∀s ∈ S(Δ)：Verdict(s) ∈ {PROVEN, WAIVED(已登记、未到期)}
            ∧ S(Δ) 内无 DRAFT 声明（未背书应然不支持放行，§4.3）
            ∧ Evidence 全部新鲜（无 STALE）
            ∧ S(Δ) 内无孤儿声明（每条 goal 沿 refines 可追溯至已背书 mission，§4.4）
            ∧ signatory=human 的声明均已完成本次 Δ 的验收签署（§五⑥——其 PROVEN 由此而来）
            ∧ 技术层验证（UT/IT/E2E/静态检查）全绿
  → 否则转人工
```

性质：

- **作用域是 Δ 不是全库**：存量未覆盖的声明不阻塞新交付，消除冷启动死锁；存量覆盖率作为独立指标在 §七 中治理，不进放行函数；
- **白名单制**：默认拒绝，举证责任在流程侧。声明图谱/注册表不完整 → S(Δ) 无法界定 → 默认拒绝；S(Δ) 内含 DRAFT 声明 → 同样默认拒绝——应然未被批准时，任何取证结果都不具放行效力；
- **豁免不是漏洞**：WAIVED 的 `waiver` 必须登记理由、到期时间与签署人（随入库背书审批，§五②），且豁免率本身是门禁的监控指标——豁免泛滥会自动收紧为人工审查。

## 七、度量体系

单一覆盖函数 + 六个健康度指标，全部可从注册表与判定机直接计算：

- **加权覆盖率** `C(G)`：分母只计**已背书且未豁免**的声明（§4.4），可按 level/业务域/feature 切片查看，但只有一个定义。**`C(G)` 禁止单独展示**——必须与**应然批准率**（已背书/已登记）和背书积压成对输出，由判定脚本强制：防止"98% + 200 条 DRAFT 积压"式的新版镀金；
- **域登记率**：已登记域/全部域（如"9/20+ router"）——`C(G)` 只度量**已登记**声明，没有域登记率相伴，100% 是自洽幻觉；weight 的取值从缺陷史反推校准（出过高严重度 bug 的域加权），不允许拍脑袋；
- **背书积压**：DRAFT 声明数量与平均滞留时长（由 `created-at` 与 `endorsement` 计算）——背书是前置咽喉（§五②），积压持续上涨说明体系正在未经批准的应然上空转；
- **证据强度分布**：变异存活率/评审分歧率——低强度证据占比高的域不可信；
- **判定新鲜度**：STALE 声明占比及平均滞留时长——体系的"应收账款"；
- **豁免率与豁免年龄**：WAIVED 的占比与超期情况——无人化的隐性负债；
- **门禁拦截率**：Gate 拒绝率及其原因分布——流程健康度（过高说明取证能力跟不上，过低说明门槛失效）。

## 八、无人化成熟度：同一模型上的刻度

成熟度不按"层"分级，而按生命周期各环节的**自动化渗透率**分级——四个档位是同一体系上旋钮的位置，不是四种体系（L1–L4 是**渗透率档位**，与声明的 `level` 字段无关）：

| 级别 | 派生 | 取证 | 判定 | 背书/签署 | 人工角色 |
| --- | --- | --- | --- | --- | --- |
| L1 人工期 | 人工 | 人工 | 人工 | 人工 | 全程 |
| L2 辅助期 | 人工+AI 建议 | AI 生成、人工评审入库 | 自动 | 人工逐条背书 | 背书 + 证据评审 |
| L3 自动期 | 规格变更自动派生 | AI 生成+异构评审+强度门 | 自动+回读 | 人工背书，AI 预审排序 | 背书 + 评审分歧与回读失败 |
| L4 无人期 | 全自动 | 全自动 | 全自动 | 入库背书仍人工；验收签署仅 human 声明与 WAIVED 到期复核 | 背书 + 门禁拒绝时介入 |

即使 L4，入库背书与 `signatory=human`/WAIVED 的人工环节**永远保留**——入库背书不设自动化档位（背书自动化 = 应然自我批准，体系即刻退化为盖章机）。这不是自动化程度不够，而是体系的诚实设计（见 §三）。

## 九、失败语义与诊断

`VIOLATED` 声明触发三叉定位，这是 ABST 区别于"测试红了就修码"的关键：

1. **实现错**（最常见）：修实现，证据复跑（复跑通过回 PROVEN，§4.3）；
2. **声明错**：意图本身有误或已过时——走声明升版流程（先改声明再改实现，升版后声明回 DRAFT 重新背书，§4.3），规格的人工评审是这里的前置锚点；
3. **证据错**：断言过强/环境脆弱（假红）——修证据并回溯其强度评审为何漏判。

`STALE` 是体系的自洁机制而非失败：**实现变更**（`impl-refs` 命中）自动传播 STALE，驱动重新取证，保证 Verdict 永远不过期宣称；**声明文本语义变更**不走 STALE，而是升版回 DRAFT 重新背书（§4.3）——两条边分别对应"实然变了"与"应然变了"，不可混淆。**落地机制**：注册表为每条声明记录 `impl-refs`（§4.1），CI 中 `git diff` 命中即自动置 STALE——靠机制而非纪律（仅靠文档纪律约束的落地必然失效）。

## 十、与技术层测试的接口

ABST 不吞并 UT/IT/E2E，两者正交：技术层管 verification，ABST 管 validation。**部署前提是技术层已建成且可信**——ABST 的判定机消费技术层结果，若输入本身不可信，放行函数失去意义。

**ABST 不是 E2E 的子项，是完全独立的体系。** 这一独立性必须贯彻到部署形态：ABST 资产（注册表、词汇表、探针、判定机、报告）独立成顶层目录（如 `<repo>/abst/`），**不得寄居在 `e2e/` 或任何技术层测试目录之下**——目录结构即架构声明，寄居会在认知与治理上把 ABST 降级为"一种端到端测试"，其覆盖率、放行、豁免随即被技术层的语义绑架。ABST 可以*调用* E2E 套件（作为委托证据），但调用关系不改变体系的并列关系。

接口只有两处：

- **放行输入**：Gate(Δ) 消费技术层的全绿信号作为条件之一（§六）；
- **判重原则**：同一应然断言只登记为一条声明、只配一份证据。技术层已锁定的单元行为若被业务声明引用，声明证据可直接委托（引用技术层测试作为 Evidence 载体），不复制用例体。

## 十一、方法论溯源：ABST 从各 DD 吸收了什么

| 方法论 | 吸收的元素 | 在 ABST 中的位置 |
| --- | --- | --- |
| TDD | 声明先行（先声明后实现）；红-绿节奏 → STALE→重新取证的自洁循环 | §五①、§九 |
| BDD | GWT 句式（证据载体）；通用语言促进协作 → 升级为词汇表约束 | §4.2、§4.6 |
| ATDD | 验收标准前置 → goal 级声明；Three Amigos 三方会审 → 背书与签署仪式 | §4.1、§五②⑥ |
| SDD | 规格单一事实来源；变更提案驱动声明 diff | §五① |
| DDD | 统一语言 → Glossary 伴生资产；限界上下文 → 词汇分区；事件风暴 → behavior 级声明挖掘 | §4.6、§五① |
| FDD | Feature 组织单元与 `<动作><结果><对象>` 句式 | §4.5 |
| CDC（消费者驱动契约） | contract 级声明的优选证据载体 | §4.2 |

吸收的判别标准：**能归一为声明、证据、判定、图谱、词汇表上的属性或环节才吸收**；凡会带来独立流程、独立层、独立 KPI 的，一律不吸收——这是 ABST 与"方法论缝合怪"的分界线。

## 十二、意图具象化规范：存量工程的首要产出

对存量工程（只有代码、或有残缺历史文档），ABST 的第一波产出**不是测试通过率，而是意图的明文落地**——产品思想、功能矩阵、声明从口头/代码/散落文档中浮现为可审查、可版本化、无歧义的文本资产。测试价值是第二波。本节规定意图具象化的具体内容与格式。

### 12.1 分工原则：AI 整理，人审每条

- **AI 是书记员，不是作者**：AI 从代码、前端调用点、历史文档反推整理草稿，标注 `derived-from`；
- **人工逐条审查是强制工序**：每条声明必须有具体的人阅读、修改或背书——批量通过等于未审查；goal/mission 级还须过 Three Amigos + 异构 AI 评审（§五②）；
- **背书是前置，不是待办**：逐条背书是取证与覆盖率的准入条件（§五②），不是体系跑完后的收尾手续；
- **人的充分参与不是成本，是目的**：逐条审查的过程就是组织对齐意图的过程，背书即权威裁决（§三）。

### 12.2 分册结构

意图资产按四册组织（注册表是机器形态，分册是人读形态，二者同源生成、不得分叉）：

| 分册 | 内容 | 声明级别 |
| --- | --- | --- |
| 宗旨册 | 产品思想、战略、生存条件——少而精 | mission |
| 功能矩阵册 | feature 清单（FDD 句式），每个 feature 标注服务的 mission、owner、状态——活的、可执行的功能矩阵 | feature 维度 |
| 声明册 | 按业务域/限界上下文分章的声明全集 | goal/behavior/contract |
| 词汇表 | 统一语言，按限界上下文分区（§4.6） | —— |

### 12.3 声明格式

每条声明在 §4.1 字段之上，明文必须显式三节：

1. **应然陈述**（`text`）：FDD 句式 + Glossary 术语；
2. **边界**（`boundary`）：适用/不适用范围的显式声明——边界不明文，判定无意义；
3. **弹性**（`elasticity`）：哪些维度可协商/可调（如阈值可配置），哪些不可动摇（如升级语义）——弹性是变化的合法通道，刚性部分是回归的保护对象。

### 12.4 歧义消除

- **可判定性检查**：禁止不可证伪措辞（"快""友好""合理"），每条声明必须能回答"什么情况下它是错的"；
- **AI 歧义检测内嵌于派生工序**：对模糊措辞、多义解读自动告警并给出候选解释，由人选择或改写——"反推误读"类错误在这一关拦截。

### 12.5 具象化的完成判据

存量工程意图具象化"完成"——即声明从 DRAFT 获准进入取证环节（DRAFT → UNPROVEN，§4.3）——的判据：

1. 每个已登记 feature 有 ≥1 条 goal 声明，且可追溯至已背书 mission（无孤儿，§4.4）；
2. 每条声明经过人工逐条审查背书（§12.1）；
3. 无词表外术语（§4.6）；
4. 每条声明的边界与弹性两节非空（§12.3）。

## 十三、落地路径

1. **注册表先行，意图具象化为首要产出**：定义声明 schema（§4.1）与稳定 ID 方案，同步建立 Glossary（§4.6）；对存量工程，按 §十二 完成意图具象化（宗旨册/功能矩阵册/声明册/词汇表）——**这本身是 ABST 的第一波交付**，没有它，覆盖率、图谱遍历、门禁全部无从谈起。首波落地是**全局准入**：四册背书完成之前不启动取证与覆盖率统计（§五②）；进入稳态后按 §五② 逐声明生效；
2. **绿地路径**：新项目从规格源（openspec）派生 → DRAFT → 背书先行（此时无实现可对照，背书对象是纯应然，成本最低），实现与取证随后并行——同一状态机天然兼容；
3. **单域试点**：选 1 个规则密集、规格完整的业务域（如调度/计费类），跑通六段流水线到 L2；
4. **门禁观察模式**：Gate 先只记录不拦截，校准 S(Δ) 界定与豁免登记纪律，指标稳定后转硬门；
5. **渗透升级**：按 §八逐环节提升自动化渗透率；指标上进看板，拦截率异常即回调。

HEHE 平台机制映射（内部参考，面向 HEHE 知识库读者）：`SP_SDD`（规格驱动链，当前属半自动层、终态人工签署）对应①派生的现状起点，ABST 的签署客观化是其升级路径；双链测试链 T→T'→OT 对应③的异构评审；`effectVerifyConf`/`goalAcceptConf` 对应④回读与⑥签署的执行底座（详见 HEHE 知识库的 dogfood 运行手册、HEHE 流程调研报告与 TDD Agent Flow 文档）。

## 十四、工具链倾向：确定性工具优先

ABST 的实践层面有一条明确的工具使用倾向：**确定性可计算的读取与分析，优先交给工具，而不是默认让模型通读**。动机有二：**token 开销**（工具一次扫描与模型逐文件阅读，成本差几个数量级）与**幻觉控制**（模型"读后转述"会编造文件、行号与行为；工具输出是可复核的一手事实）。这是 §二"确定性与概率性分离"在实践层的延伸。

**这是倾向，不是前提。** 用户的项目不一定有 openspec，本地环境也不一定有下列工具——缺位时对应环节退化为模型/人工直接执行，体系照常成立，只是成本与幻觉风险回升。退化执行时必须遵守一条底线：**给出可复核的出处**（文件 + 行号/锚点），并自知这是弱证据、评审优先级相应提高。有工具则补工具，是落地过程中持续还债的方向。

| 生命周期环节 | 工具倾向 | 工具缺位时的退化形态 |
| --- | --- | --- |
| ① 派生 | openspec（规格库 diff、变更提案）——规格源的工具化读取 | 直接读需求文档/代码，但结论必须标注 `derived-from` 与出处 |
| ② 背书（评审材料） | codegraph / LSP（声明 → 实现影响面、`impl-refs` 候选清单） | 人工或模型翻代码定位，逐条给出文件+行号 |
| ③ 取证 | schema 静态解析生成 manifest（zod/OpenAPI）；ast-grep/semgrep 定位证据锚点 | 手工梳理端点清单，锚点逐个核对 |
| ④⑤ 执行与判定 | abst engine（本仓库 `bin/abst`）+ CI | 不降级——判定机是体系支点，无替代 |
| 评审 | open-code-review 类自动评审工具先行，异构模型复核语义，人裁决分歧 | 异构模型 + 人工会审兜底 |
| 静态扫描 | semgrep/CodeQL 等的产出可直接登记为 contract 级声明的 Evidence | 无则不登记此类证据，不留空口断言 |

约束：

- **事实性内容优先取自工具输出**；无工具时，模型对代码的转述必须带可复核出处（文件 + 行号），否则不得进入注册表与证据链；
- 工具覆盖不到的语义判断（应然是否合理、意图识别、分歧裁决）仍是模型与人的工序，不强行工具化；
- 工具清单是开放的，判别标准不变：**确定性、可复核、产出机器可读**。
